# ADR 0032: Writer-safe dev API rollout and recovery

- Status: implemented in source; cloud operation requires the protected dev workflow and separate verification.
- Supersedes the image-only and operator-owned health portions of [ADR 0013](0013-dev-kubernetes-cd.md) and [ADR 0026](0026-native-hosted-studio.md). The owner's 2026-10-31 request adds health verification and bounded recovery.

## Context

The co-located dev host owns one Global and one Region SlateDB writer. A Kubernetes `Recreate` Deployment with one replica does not provide uninterrupted service: the old process must drain, close the databases and release ownership before the new process can start. A successful image patch does not establish readiness. A bad binary or configuration can leave Netlify unable to reach the API. Rolling back an image does not reverse writes, migrations, provider effects, or writer ownership, and an old binary is not automatically compatible with data written by a new one.

## Decision

Use the existing protected, serialized, main-only dev CD workflow. Before an image change require an immutable current image, one replica and `Recreate`, a configured readiness probe, fully observed and ready Deployment, no legacy-retirement flag, and a healthy public baseline. Capture the previous image digest, Deployment UID, generation, resource version and Pod template. Apply only the selected container image with a resourceVersion-guarded strategic patch. Confirm the exact updated template and generation, wait for rollout, and verify observed/ready/available/updated counts, the public metadata-backed health endpoint, auth configuration, and denial of an unauthenticated Workspace list. Public checks use bounded retries of read-only requests. These checks do not establish provider functionality or validate a real account login.

A rollout failure marks the release failed even if recovery succeeds. Automatic recovery is disabled by default. A protected `DEV_ROLLBACK_POLICY` environment variable can list **individually reviewed** entries of the form `[{"sourceSha":"<40 lowercase hex>","previousDigest":"sha256:<64 lowercase hex>","storageCompatible":true}]`. The entry attests that the prior binary can safely read all persistent states and effects the exact candidate may have produced, including partial startup and migrations; it is not inferred from a successful previous release. Only an exact source SHA and prior digest match permits recovery, and only if the unchanged Deployment is observed at the expected generation with no ready/available replica. Restore only the previous image using the current resourceVersion, then independently verify rollout, identity, public health and unauthenticated denial. Fail closed if the update result is ambiguous, the Deployment or template changes, a writer release is uncertain, evidence is missing, or only the public gateway check fails. Never delete owner records, force-release ownership, reset storage, undo a whole Pod template, or retry a possibly applied mutation blindly.

An explicit protected `recover` dispatch accepts exact failed and recovery digests and `storage-compatible` confirmation after an operator verifies data compatibility and writer ownership. It requires the exact observed failed image and zero ready/available replicas, uses the same image-only guarded patch and checks the resulting deployment and public API. It does not bypass CI or claim to resolve an uncertain SlateDB owner. Preserve source and previous-image digest evidence outside transient logs for incident response.

## Consequences and verification

These protections reduce time spent serving a broken release and prevent silent green deployments; they do **not** guarantee zero downtime, automatic repair in every failure, or 500-free operation. For availability during upgrades, separate the API serving tier from independent Meta authorities, use explicit safe ownership transfer/fencing, and verify the actual deployment topology and failure behavior before enabling multiple replicas. Recovery when an old writer might still run requires a separately proven fencing protocol. Existing S3 roots and keys are never replaced as a workaround.

Regression tests use simulated Kubernetes/HTTP failures and cover preflight, stale revisions, uncertain patch responses, incompatible/missing policy, observed unready rollback, public-only failures, and manual recovery. Live acceptance additionally needs a controlled isolated canary or fault-injection target; a unit test does not prove Kubernetes, Netlify or object-store behavior. This dev workflow still requires exact-commit CI and the protected `dev` environment.
