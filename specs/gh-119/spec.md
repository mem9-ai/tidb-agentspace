# GH-119: Workspace audit and request history

- Status: proposed design; not implemented. Parent intent: [GH-119](https://github.com/mem9-ai/tidb.ai/issues/119).
- Source baseline: `9ad45f75e0263da00787ed813190a9d2a92a042b`.
- Authority: Workspace Key and regional security decisions; [security design](../gh-84/openapi-security.md), section 7, and [metadata scale](../gh-74/metadata-scale.md).
- Delivery: separate reviewed design revision before implementation; this specification does not claim audit completeness or authorize changes to deployment or credentials.

## Outcome and current boundary

A Workspace owner needs to investigate a failed integration and understand who changed access or data. They need two distinct views: HTTP request diagnostics and security/operation audit. Today the product exposes at most 200 recent successful mutation events. It does not expose request status, latency, or a complete record of denied and failed actions. The existing event feed must retain that label and must not be presented as a complete audit trail.

## Scope and contracts

1. **Request history** records bounded metadata for authenticated Workspace API requests: server-generated event and correlation IDs; authority and Region; validated Workspace and actor/Key identity; an allowlisted operation name and HTTP method; status class/code; timestamps and elapsed time. Never store raw URLs, paths, query strings, request or response bodies, SQL, commands, file content, headers, cookies, IP addresses, provider errors or credentials. Unknown operations use a fixed safe label. Log reads themselves are excluded from this stream to avoid recursion.
2. **Audit history** separately records security and data-changing operations, access decisions, outcome, actor, validated Workspace and authorized target identity, operation/correlation ID and timestamps. Distinguish attempted, succeeded, denied, failed and unknown outcomes; a timeout after provider I/O is not a confirmed failure. Do not reconstruct prior events as if they had complete coverage. An event is attributed to a Workspace only after its identity and authority are verified; invalid credentials or attacker-selected Workspace IDs must not create records visible to another tenant.
3. Specify operation coverage per Global and Regional authority and expose an explicit coverage/start time and degradation indicator. A first implementation must cover Key lifecycle, resource lifecycle, file writes/deletes, query writes, permission denials after trusted authentication and provider failures for those operations; Global and Region coverage must not be silently combined or attributed to the wrong authority. Unattributable authentication failures remain platform-only and are reported as a coverage limitation.
4. Provide separate versioned, cursor-paginated regional Workspace API list operations for request and audit records, plus explicit coverage metadata. Propose `GET /workspaces/{workspaceId}/request-history` and `GET /workspaces/{workspaceId}/audit-history`; no Console-only data path. Specify Global operations separately where their source of truth lives. Stable opaque cursors, descending time plus unique-ID ordering, limits of 1–100 and bounded time filters prevent unbounded scans. No query takes a customer-supplied raw storage key or tenant identifier as authority.
5. Initially restrict these reads to an authenticated Workspace Owner. Workspace Keys must not inherit access from broad existing resource scopes. Any later Key access requires an explicitly designed new action scope, resource-aware filtering, OpenAPI update and separate authorization tests. Read authorization is rechecked on every page and cannot reveal another Workspace or internal backing File System.
6. Keep request history and audit in durable, tenant-scoped regional storage with distinct indexes, bounded retention and capacity. Default retention is at most seven days and 100,000 request records per Workspace; eviction is oldest-first and disclosed. Audit records default to at most 30 days and 100,000 entries per Workspace and authority; whichever limit is reached first determines the visible window. Expose retention and truncation watermarks; this is product history, not a compliance certification. Encrypted metadata, per-Workspace limits, bounded write queues and admission control prevent one tenant from exhausting the service.
7. Acknowledged security mutations require a durable audit intent coupled to their authoritative operation or an equivalent recoverable journal. If audit intent cannot be durably recorded, reject before external side effects. After an uncertain provider action, retain an inspectable unknown outcome and never replay the mutation automatically. Request diagnostics may be dropped under overload only with visible aggregate loss/degradation; an observability failure must not leak sensitive values or turn a completed operation into an ambiguous automatic retry.
8. The Activity destination offers separate Audit and HTTP requests views, searchable by safe fields, with empty, loading, failure, pagination, retention and coverage states. It must distinguish the legacy successful-event feed from new audit records and avoid calling partial data a complete audit. Dates, actors and statuses are readable at 1280×800 and 390×844 in Light and Dark. Console behavior consumes the same authenticated API as other clients.

The boundary and initial policy choices are proposed in [ADR 0044](../../docs/decisions/0044-workspace-observability.md). The implementation must specify the exact published schema, validation/error codes, event-type allowlist and generated OpenAPI change before shipping. This design does not grant provider keys, expose native credentials, or change query/file execution privileges.

## Initial API shape

The following is the proposed contract to be generated and tested during implementation, not an existing endpoint. Both responses are `Cache-Control: no-store` and use `application/json`; timestamps are RFC 3339 UTC strings, identifiers are server-issued bounded strings, and durations are nonnegative milliseconds. Missing authentication returns 401; an authenticated actor without owner authority returns 403; a Workspace outside the principal's authority returns a non-disclosing 404. Unavailable storage returns 503 with a safe error code. No list call performs provider I/O.

| Operation                                              | Authority and actor                               | Response                                                                   |
| ------------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------------------------------- |
| `GET /api/v1/workspaces/{workspaceId}/request-history` | Selected Global or Region, verified owner session | `data` request records, `nextCursor`, `coverage`, `retention` and `health` |
| `GET /api/v1/workspaces/{workspaceId}/audit-history`   | Selected Global or Region, verified owner session | `data` audit records, `nextCursor`, `coverage`, `retention` and `health`   |

A request record contains `id`, `requestId`, `authority`, optional `regionId`, `actor` (`kind` and opaque `id`), `operation`, `method`, `status`, `startedAt` and `durationMs`. An audit record contains `id`, `operationId`, optional `requestId`, `authority`, optional `regionId`, `actor`, `action`, `target` (allowlisted type and authorized opaque ID), `decision`, `outcome`, `occurredAt` and `updatedAt`. Neither schema admits arbitrary metadata maps. Omit unavailable trusted fields rather than deriving them from untrusted request text. Global records do not invent a Region.

Lists accept `limit` (1–100, default 50), optional bounded `from`/`to`, and optional opaque `cursor`. A malformed cursor or invalid range is 400; a cursor outside its retained window is 410 with an explicit restart instruction. A cursor is scoped to Workspace, authority, stream and filters and cannot be reused across them. `coverage` provides its start time, allowlisted covered operations and known exclusions; `retention` gives configured limits, earliest retained record and truncation; `health` gives a bounded status and dropped count for request diagnostics. Counts must not leak other Workspaces. A user can refresh the first page and continue without changing application data.

## Acceptance cases

| ID     | Case                                                                                                  | Required evidence                                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| OBS-01 | Owner lists request records in stable pages; empty, expired and degraded coverage are explicit.       | Native API/Console cases; restart and concurrent inserts.                                                            |
| OBS-02 | A verified actor performs an authorized action, a denied action and a failing provider operation.     | Correct authority, operation, outcome, correlation and timestamps; no invented success.                              |
| OBS-03 | Missing, revoked, expired, cross-Workspace and resource-scoped credentials request or create records. | Native negative cases prove no other tenant's records/identities leak, including forged Workspace IDs.               |
| OBS-04 | Inputs contain bearer tokens, SQL literals, file bytes, query strings and sensitive headers.          | Storage, API output, operational errors and tests contain none of those values.                                      |
| OBS-05 | Concurrent calls, restarts, retention eviction and cursor replay occur.                               | Bounded durable ordering, no cross-tenant effects, documented gaps; no automatic side-effect replay.                 |
| OBS-06 | Audit journal unavailable before mutation, or outcome becomes unknown after provider I/O.             | Fail before side effects when required; otherwise report/retain uncertain outcome and reconcile without retry.       |
| OBS-07 | Request ingestion saturates, storage fails, or a log-list request is made.                            | Bounded workload, explicit diagnostic loss/degradation, no recursive logging and no silent audit-completeness claim. |
| OBS-08 | Existing clients and legacy event records remain in use.                                              | No migration deletes data or changes existing grants; legacy success-only records remain accurately labeled.         |
| OBS-09 | User opens both views, filters and pages, encounters an error and returns later.                      | Desktop/narrow, Light/Dark and keyboard checks against the real API contract and recorded screenshots.               |

## Dependencies and implementation gates

The owner has requested both views. The proposed retention, authority boundaries and journal semantics are project design choices, not assertions about existing functionality. Review the ADR and pin the accepted spec revision before implementation. The implementation must update `server/generate-openapi.mjs`, generated contracts/client types, relevant Rust domain and API tests, and the Console together. Run `npm run check` and impact-scoped native authorization, S3/metadata persistence and browser cases; retain enforced CI protections. No live test may disclose production secrets or irreversibly modify customer data.
