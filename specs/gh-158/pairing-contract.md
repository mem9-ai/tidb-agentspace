# GH-158: Guest Agent pairing contract

- Status: draft for review; no pairing operation in this document is implemented.
- Task: [GH-158](https://github.com/mem9-ai/tidb.ai/issues/158); parent: [GH-150](https://github.com/mem9-ai/tidb.ai/issues/150).
- Accepted journey: [GH-150 at `5ea06a3f9edfb6dbf471c217ee2cd1b112888ee1`](https://github.com/mem9-ai/tidb.ai/blob/5ea06a3f9edfb6dbf471c217ee2cd1b112888ee1/specs/gh-150/spec.md), especially AF-04, AF-05, AF-09, AF-A3 and AF-A6.
- Source baseline: `1c15fee`. Security dependencies: ADRs 0036, 0037, 0041 and 0043. A separate ADR and reviewed machine-readable OpenAPI amendment are required before implementation.

## Outcome

A Guest connects an external Agent without putting a Workspace Key in a prompt, command argument, URL, log or history. The Agent starts a short-lived attempt using a secret verifier held by its local client. The Guest signs in to the existing Workspace, enters a separate code and explicitly approves the exact resources, actions and expiry. The verified client redeems once and keeps its Key in a local secret store. A genuine authenticated regional request is required before the Console displays a connection.

This contract covers authorization and connection, not an Agent's analysis or report provenance. GH-159 covers task evidence. Sign-in does not retain a Guest Workspace; GH-160 covers explicit account copying. Existing manual Key management remains available under its current policy.

## Authority and disclosure

Global owns pairing and Key issuance. The Region remains authoritative for resource access and current Guest policy. Use the existing single-entry and Portal route families; no Agent receives Owner, Key-management or resource-creation privileges from pairing. Co-located Guest bridging follows ADR 0037; unsupported independent deployments fail closed and do not pretend to have connected an Agent.

Workspace IDs and attempt IDs identify resources, not credentials. A pairing code permits lookup only inside the matching authenticated Guest/Owner Workspace; it cannot approve or redeem. The verifier is a secret: send it only in a TLS request body to the configured trusted Global origin and keep it outside prompts, command arguments, URLs, diagnostics and history. Key material is returned once directly to the verifier-bearing client. Never log either value or emit it in a Console event, server error, OpenAPI example, screenshot or telemetry.

## Lifecycle

An Agent client generates a random 32-byte verifier and sends its SHA-256 challenge with the Workspace ID. Encode both values as unpadded canonical base64url; compare the computed digest in constant time. Global creates a cryptographically random opaque attempt ID and a separate twelve-character code drawn uniformly from uppercase RFC 4648 base32 (60 bits of entropy), with a maximum five-minute lifetime, shortened to the Workspace expiry. Display grouping characters locally; normalize and validate before lookup. The response shows the code and deadline to the user, but contains no Workspace Key. A secure owner lookup uses an explicit code in a request body, not a URL. The user sees the precise Workspace, selected resources, scopes, expiry and the fact that `files:write` permits create, update and delete across each selected resource. No resource, future-resource wildcard, database action or Key administration is silently granted.

Approval is an explicit authenticated, origin/CSRF-protected action. It binds the attempt to the approved normalized grants and does not issue credentials. Each approval must recheck current ownership and Guest policy. Cancellation and expiry are terminal. A client polls with the original Workspace ID and its verifier in a request body; the ID selects the Workspace metadata partition and is never authorization. Responses before redemption contain no credentials. A separate redemption validates verifier, approved state, exact Workspace and current expiry, and atomically records consumption and issues at most one distinct scoped Key. The new Key and durable consumed-attempt receipt, including the Key ID, belong in the same transactional metadata partition. A compare-and-swap on the approved version fences concurrent redemptions and cancellation. A secret is returned only if the commit is confirmed to contain that invocation's verifier and Key. The Key expires no later than Guest access.

Global stores a challenge and verifier for the random Key, never either plaintext secret. Approval grants use the existing immutable grant mechanism and must be durably confirmed before the atomic redemption. Policy installation uses the existing Region delivery boundary; `pending` and `applied` remain distinct. No UI may infer an applied grant from Key creation or a successful copy action.

If a redemption response is lost, the attempt might have been consumed. A replay must never issue another Key or return the original secret. The owner can inspect the attempt and associated Key ID, revoke it using existing Key management, wait for applied regional revocation, then explicitly start a new attempt. A timeout or failed delivery never reports a successful connection. Starting a new attempt does not implicitly revoke an earlier one.

## Code indexing and bounded state

Store a versioned HMAC-SHA-256 digest of the normalized code and Workspace ID using an unambiguous, length-prefixed encoding, never the code itself. The index and attempt are committed atomically within the Workspace's Global Key metadata partition, with collision detection and a newly generated code on collision. Keep the index-key material in the existing protected Global secret boundary; retain the previous key version only long enough to look up still-live attempts during rotation. Do not reuse a key from token signing or any provider credential. Both code and verifier checks must avoid disclosing which comparison failed. A successful lookup is allowed only after matching Guest/Owner Workspace authentication and the existing origin/CSRF checks.

Bound request bodies, identifier length, number of resources and scopes before durable work. Admit no more than five live attempts per Workspace and enforce the peer and failed-verifier limits stated below before accepting new writes. Terminal or expired attempts lose their code index and are removed in bounded, retryable cleanup; do not allow abandoned attempts or random nonexistent Workspace IDs to create unbounded state. Persist at most one owner-visible, content-free connection receipt per issued Key, expiring no later than the Key or Guest access. Retention describes visibility and access, not immediate deletion of older object-store versions. On metadata, cleanup or admission failure, return an availability error and do not create an additional Key.

## Guest logout and the two-authority boundary

Global Key metadata and the Region Guest policy do not share one transaction. Do not claim they do. The Region's durable Guest-policy denial is the logout linearization point. Redemption checks current policy before issuance and rechecks it after the atomic Global Key commit before releasing the one-time secret. If the latter check fails or is unavailable, return no secret and preserve the issued Key ID as a denied or unknown outcome. This can leave a Key record, but it is not a usable connection and must remain subject to cleanup and the Guest's original expiry.

The system must independently deny Global Key exchange after durable Guest denial and reject every Region data admission against the current Guest policy. A Token issued before or racing with logout must fail Region admission after logout completes; any already admitted operation follows the existing drain policy. Region policy installation for the new Key must not reactivate a denied Guest. These checks must use authoritative, monotonic policy state across replicas, not a cached browser session or a best-effort callback. Where that guarantee cannot be enforced for a deployment topology, pairing stays disabled there. Native races must place logout before, during and immediately after the Global commit, before and after token exchange, and before and during regional admission. They must establish that no usable credential survives acknowledged logout, even if an orphan Global Key record exists.

## First external client

Target Codex CLI with an MCP connection first, while retaining a client-neutral pairing API. The local sidecar or MCP transport owns the verifier and Key; prompts contain the task and non-secret Workspace identity only. The proposed client must explain exactly what is installed and where credentials are stored, offer an explicit disconnect, and avoid modifying an existing user Agent configuration silently. Use a disposable isolated client profile for acceptance; never use or overwrite a user's real credentials or MCP configuration as test data. Pin a minimum supported Codex version only after observing an actual complete connection and task, not merely from CLI help or a mocked MCP client. Select and review the MCP transport, local secret-store behavior, dependency distribution and recovery before implementation; no one-line setup or real-client compatibility is claimed yet.

The Region derives the Key ID from the verified scoped authorization, never from the request body or an untrusted task reference. A receipt records only Workspace, Key and resource IDs, Region and server time, without file contents, SQL, peer address, Agent vendor or credential. Authorize `files:read` and the selected File System before committing; recheck the live credential under the existing Region policy lease at the effect boundary. One bounded record per Key is enough; keep it no later than Key or Guest expiry and remove it with bounded cleanup. Repeated receipt requests can observe or refresh that Key's record but cannot extend access, mint a credential or bypass a revocation fence. An Owner or Guest observes it using a separately authenticated regional Portal route, with the Key ID obtained from the Global pairing attempt. Ordinary request history does not receive this content.

After approval the Console may show `Waiting for your agent`. It may show `Connected` only after the receipt for that exact issued Key and Workspace is returned, and only while the currently inspected Key and Region policy support that state. A stale receipt is historical evidence, not proof that a revoked or expired Key remains connected; show the timestamp and current revocation/policy state separately. This receipt proves an authenticated request, not data analysis or authorship of any report. GH-159 requires separate evidence for those outcomes. The receipt schema and its delivery boundary still require review before implementation.

## Error contract

Use the existing structured error envelope and request ID. Proposed codes are `INVALID_INPUT` (400), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `PAIRING_NOT_APPROVED` or `PAIRING_CONSUMED` (409), `PAIRING_EXPIRED` (410), `PRECONDITION_FAILED` (412), `PRECONDITION_REQUIRED` (428), `RATE_LIMITED` (429) and `SERVICE_UNAVAILABLE` (503). A wrong verifier, unknown attempt or different Workspace is `NOT_FOUND`; do not disclose which comparison failed. Approving an unowned resource or unsupported scope fails before any issuance or provider effect. A version conflict never applies the stale change.

Rate-limit responses may contain a bounded `Retry-After` for the caller's own exhausted limit, without disclosing another Workspace. `SERVICE_UNAVAILABLE` does not imply whether a redemption commit happened. A client must observe the attempt and, when consumed, use Owner inspection and explicit Key revocation; it must never interpret a 503 or lost response as a reason to mint another Key. Unauthenticated responses and diagnostic streams never include the challenge, verifier, code, Key, cookie or raw provider error.

## Limits and recovery

All pre-authentication operations require server-enforced bounded admission, durable attempt and verifier-failure limits per Workspace and trustworthy network peer, expiration cleanup, and non-disclosing errors. Proposed initial caps are five active attempts per Workspace, 20 initiation requests per network peer per ten minutes, five wrong verifiers per attempt, and ten unsuccessful authenticated code lookups per Workspace per ten minutes. Exhaustion returns a typed `429` without creating a Key; expiration does not reset another active limit. Reject new operations if the durable limit store is unavailable. Derive the peer from the actual transport or an explicitly configured trusted proxy; never trust a client-supplied forwarding header. Persist a keyed digest rather than a raw address, rotate the key according to a documented policy, and remove the associated counter within its bounded window. These controls must work across replicas and restarts; an in-memory counter, browser restriction or an assumed proxy limit is not sufficient. The precise transactional counter and bounded cleanup mechanism must be reviewed and load-tested in the amendment. Until they exist, do not expose public initiation or lookup.

For the proposed distributed limiter, commit the network-peer window reservation before Workspace admission; a later rejection may consume that rate allowance but can never issue a Key. Store peer buckets as time-bounded, keyed digests in a system-owned Global metadata partition with conditional updates and bounded sweeping. Enforce a configured fleet-wide cap on live admissions as well as the peer cap, with bounded sharding to avoid one global hot record; fail closed if any required reservation cannot be confirmed. Validate that a Workspace is eligible before creating Workspace-scoped attempt records, and return the same non-disclosing error for nonexistent and ineligible Workspaces.

Within each eligible Workspace, a conditional transaction creates the attempt, code index and one of at most five active-slot records. Approval or observation cannot allocate a slot. Consumption, cancellation and expiry remove the active slot atomically with the terminal state; bounded admission may first reconcile expired slots. Neither a crash nor a duplicate cleanup can decrement the slot count twice. Wrong-verifier and authenticated-lookup windows likewise use conditional records, bounded expiry and server-side cleanup. These are design requirements, not a claim that the current metadata service provides automatic TTL or that sharding defaults have been load-tested.

An interrupted initiation can leave an unissued, expiring attempt; starting another explicit attempt is safe only within the admission limit. A lost approval response is inspected before repeating. A lost redemption response is an unknown effect, never a reason to mint another Key. A missing or unavailable policy service is an explicit retryable availability error, not permission to bypass validation. Expiry, Guest sign-out, verifier mismatch, cross-Workspace lookup, reused codes and concurrent approval/redemption/cancellation must fail closed. Enforce Guest logout's existing drain/revocation guarantees across the issuance boundary; the implementation must prove this with a race test, not assume two separate metadata checks are atomic.

The client persists the Key only in an explicitly chosen local secret store with restricted access. It must never print the Key, append it to shell history, or write it to a source tree. Failure to persist after redemption is a lost-secret outcome: revoke that Key and start a new attempt. Verify one named external Agent client end to end before claiming support; a test HTTP client or a copied prompt is not evidence of a real Agent.

## Acceptance and implementation gate

1. A verified external client starts a challenge; a Guest explicitly approves a single selected File System and the exact scopes. No Key exists before approval and no other resource is granted.
2. Wrong Workspace, guessed or expired code, wrong verifier, replay, duplicate concurrent redemption and cancellation races do not issue a usable Key. Rate and storage bounds hold across two server instances and restart.
3. Region policy pending, failed or unavailable does not appear applied. A connected state requires a server-confirmed authorized Region request by the issued principal, not a client claim.
4. Logout, expiration and revocation races are tested before and during issuance and after Region policy apply. Denial is durable after restart, including a delayed old token or stale approval.
5. Lost response after commit never repeats issuance or reveals the secret. The user can inspect the affected Key and revoke it; denied and unknown outcomes remain distinct.
6. Native and OpenAPI tests cover both authorities, state schemas, permissions, side effects and recovery. Browser assertions cover approval, denied/pending/expired/connected/revoked states in desktop/narrow and light/dark modes. Separately record the external Agent client, source/deployed revision and observed time.

This draft is not an authorization to modify public contracts or widen credentials. Complete and review the ADR, machine-readable schema, distributed admission and authenticated receipt design before implementation. Preserve existing Key and Guest data; do not deploy or migrate a customer Workspace as a test.
